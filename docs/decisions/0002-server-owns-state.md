# 0002 — Server 拥有 Agent 状态，客户端只留设备级偏好

**状态**：已采纳
**影响阶段**：0（协议）、2（主题）、3（持久化）、4（硬切换）

## 背景

旧实现把所有状态放在客户端的 SQLite 里（`userData/kowork.db`，12 张表）：项目、会话、排队请求、
运行、事件、审批、路径授权、Koaks 的完整 turns/items/checkpoints、压缩检查点、供应商、
模型 Profile、应用设置。API Key 由 Electron `safeStorage` 加密存在本机。

引入远程 server 后必须回答：这些状态归谁？

## 决策

**按"换一台电脑接同一个 server 时，这个状态应该跟着走吗"来切分。**

归 **server**（走 KAP，存在 server 的数据库里）：

- 项目、会话、排队请求、运行、事件、审批、路径授权
- Koaks 的对话记忆与压缩检查点
- 供应商、模型 Profile、**API Key**
- 默认模型 Profile、默认权限模式

归 **客户端**（不进协议，存在本机 `userData/client-settings.json`）：

- 主题、强调色
- 背景图片及其模糊度/透明度
- 面板宽度与布局
- 界面语言
- 连接配置（本地/远程、host、port、密钥）

## 理由

**判据必须是单一且可机械套用的**，否则每加一个设置项都要重新辩论一次。"该不该跟着服务器走"
这条判据能直接给出答案：权限模式影响 server 上的真实文件操作，必须归 server；主题是这台
显示器上的审美偏好，必须留在客户端。

**对话历史归 server 是远程模式的核心价值。** 用户在公司电脑上发起的任务，回家用另一台电脑接同一个
server 应该能看到完整进度。如果历史存在客户端，远程模式就退化成了"共享一个模型 API 代理"。

**API Key 归 server 是被 0001 强制的**，不是选择。server 要调用 LLM，就必须持有密钥。

## 后果

### 安全语义变更（必须明确记录）

旧架构里 API Key 从 renderer 的表单**直接**提交给 Electron Main，走一条独立的 IPC 通道，
刻意绕开 Core RPC，再由 `safeStorage` 加密。密钥从不进入应用 DTO、事件、SQLite 或日志。

现在密钥必须随 KAP 上行到 server。这是一次真实的攻击面扩大，配套约束：

- 客户端对**非 loopback** 地址默认强制 `wss://`；允许降级需要用户显式确认
- server 侧加密落盘，`credentialConfigured` 只报告"存了没有"，密钥**永不回传**
- 凭据改动走独立的 `providers.setCredential`，与普通字段更新分开，便于审计

### 其他后果

- 客户端不再有数据库。`packages/core` 与 `src/core` 整体删除（阶段 4）。
- 首次连接一个新 server 时，用户看到的是空项目列表 —— 项目属于 server。这需要在 UI 上说清楚，
  避免用户以为数据丢了。
- `settings.*` 只承载 ServerSettings。客户端设置不进协议，因此不需要 server 支持就能演进
  （阶段 2 的主题体系完全不依赖阶段 3）。

## 什么情况下应该推翻

如果将来要支持"多个客户端共享同一份主题配置"，那主题就需要一个归属明确的存储位置。但更可能的
正确做法是加一个独立的用户配置同步机制，而不是把设备级偏好塞进 Agent 协议。
