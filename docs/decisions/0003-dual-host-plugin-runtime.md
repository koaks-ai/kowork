# 0003 — 插件双宿主：UI 半在 renderer，Agent 半在独立进程

**状态**：已采纳
**影响阶段**：1（设计系统）、5（插件系统）

## 背景

需求有两部分：

1. 右侧栏的每一张卡片都应该是插件，用户可自由添加与开发
2. 插件要能用上 Koaks 的四个 hook 点（模型请求前/后、工具调用前/后）

难点在于这两部分**跑在不同的机器上**。UI 在客户端的 renderer 里，而 hook 必须在 Koaks Agent
所在的进程里执行 —— 按决策 0001，那是 server 侧。

考虑过四条路：

1. **双宿主** —— 插件分 UI 半与 Agent 半，各自跑在该跑的地方
2. **只在客户端** —— hook 通过反向 RPC 回调客户端执行
3. **WASM** —— 插件编译成 WASM，在 server 里跑
4. **声明式** —— hook 只能用配置表达，不能写代码

## 决策

**选 1：一个插件包含两个可选的半边。**

- `ui` 半：ESM 模块，跑在 renderer，用注入的 `PluginUiKit`（设计系统原语的版本化子集）渲染
- `agent` 半：Node 模块，跑在紧邻 agent server 的**独立插件宿主进程**，消费四个 hook 并可注册工具

两半都是可选的：只做一张卡片的插件不需要 `agent` 半；只做 hook 的插件不需要 `ui` 半。

## 理由

**方案 2 会让每次模型请求都多一次跨网络往返。** hook 在模型请求与工具调用的关键路径上。远程
模式下把它反代回客户端，意味着每一步 agent 循环都要等一个网络 RTT，而且客户端断线会直接卡住
server 上的 run。这个代价不可接受。

**方案 3 的开发体验太差。** 插件作者要写 Rust/C 并编译成 WASM，还要面对 WASM 里没有网络与文件
IO 的现实（大部分有用的 hook 都需要其中之一）。这会让"用户可自由开发插件"变成一句空话。

**方案 4 表达力不够。** 用户想要的是"在工具调用前检查参数并可能拒绝"这类逻辑，声明式配置无法
覆盖。

**方案 1 让每半边都跑在原生环境里**：UI 半就是普通 React 组件，Agent 半就是普通 Node 模块。
插件作者用熟悉的技术栈，两半通过插件 id 关联。

## 后果

### 信任模型（必须明确记录的取舍）

UI 插件在 renderer 的**同一个 realm** 里执行，不做 iframe / Worker 强隔离。因此
`PluginPermission` 对 UI 插件是**告知性**的，不是强制沙箱边界 —— 一个恶意 UI 插件在技术上
能访问 renderer 里的任何东西。

这么做的原因：插件的核心价值是渲染 Inspector 卡片，需要与宿主共享设计系统、主题变量与
React 上下文。iframe 隔离会让卡片无法参与统一的动画与主题，也拿不到宿主的滚动/布局上下文，
插件体验会明显割裂。

对应的约束：

- 安装时**必须**向用户展示权限清单并要求显式确认
- 文档里必须说清"安装 UI 插件等同于信任其作者"
- Agent 插件跑在独立进程，权限对它**是**可强制的（这一半是真沙箱）

如果将来 UI 插件生态出现安全事件，应新写决策记录评估 iframe + 受控消息通道的方案，代价是
放弃部分视觉一致性。

### 热加载

两侧都要支持不重启的热加载：

- UI 半：动态 `import()` + 缓存击穿
- Agent 半：**不能重建 Koaks Agent**。做法是注册一个稳定的转发 Hook 实例与一个
  `LazyToolSource`，重载只替换它们背后的查找表。插件世代号进入 Agent 缓存 key 仅用于让客户端
  判断视图是否过期，不触发 Agent 重建。

### 对阶段 1 的前置要求

阶段 1 必须先建好 Inspector 卡片注册表并导出版本化的 `PluginUiKit`，否则阶段 5 无处挂载。
现有三张内置卡片（状态信息、上下文窗口、会话指标）在阶段 5 改写为插件，用来验证 API 够不够用
—— 如果内置卡片需要走后门才能实现，说明 API 设计有缺口。
