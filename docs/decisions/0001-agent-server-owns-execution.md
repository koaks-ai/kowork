# 0001 — Agent Server 拥有全部执行，客户端是纯展示层

**状态**：已采纳
**影响阶段**：3（服务端实现）、4（硬切换）

## 背景

原始需求是"用户可以选择本地或远程自部署的 Agent"。远程模式下工作目录在服务器上，Koaks 的
工具调用必须完全在服务器上发生。

问题在于旧实现的 9 个工具（`list_files`、`glob_files`、`read_file`、`search_files`、
`edit_file`、`write_file`、`run_command`、`git_status`、`git_diff`）全是 TypeScript，跑在
Electron 的 `utilityProcess` 里，直接操作本机文件系统与 shell。

考虑过三条路：

1. **Kotlin 单实现** —— 工具全部用 Kotlin 重写，跑在 server 上
2. **双实现** —— TS 版留给本地模式，Kotlin 版给远程模式
3. **Node 远程代理** —— 工具仍是 TS，server 反向 RPC 回客户端执行

## 决策

**选 1：工具用 Kotlin 单实现，永远在 server 上执行。本地模式跑一个 sidecar 进程，代码路径与
远程完全一致。**

客户端只负责：展示、审批、文件上传、预览。它不碰工作目录，不执行工具，不调用 LLM。

## 理由

**方案 2 会产生两套需要逐字节对齐的权限实现。** 工具的危险面不在功能而在权限：路径
canonicalize、symlink 真实路径校验、项目边界判定、敏感环境变量剔除、进程组终止。两套实现意味着
每条安全规则都要写两遍并保证语义一致 —— 而"本地模式的路径校验有个洞、远程模式没有"这类 bug
几乎不可能靠测试发现。安全边界必须只有一份实现。

**方案 3 让远程模式失去意义。** 用户选远程部署的目的就是让代码与命令跑在服务器上。把工具执行
反代回客户端，等于服务器只是个模型调用中转，工作目录仍在本机。

**方案 1 让"本地"变成"远程的一个特例"。** 本地模式只是把 server 跑在 `127.0.0.1` 上。这带来
一个很大的隐性收益：**本地模式的每次使用都在测试远程模式的代码路径**。两种形态不会出现各自的
专属 bug。

## 后果

- 9 个工具要用 Kotlin 重写一遍（阶段 3d）。这是本次重构最大的一块工作量，无法避免。
- 客户端不能再用 Electron 的原生目录选择对话框选项目根 —— 那会选到本机目录。必须实现自己的
  目录选择器，走 `fs.browse`（阶段 4）。
- 本地模式多了一个进程与一次 WebSocket 往返。对交互延迟的影响可忽略（loopback），换来的是
  代码路径统一。
- Electron 打包需要带上对应平台的 sidecar 二进制（阶段 6）。

## 什么情况下应该推翻

如果将来出现"必须访问客户端本机资源"的工具需求（例如读取用户本机的浏览器 cookie、调用本机
GUI 应用），那就需要在协议里补一个受限的反向 RPC 通道。届时应新写一条决策记录，而不是悄悄
在工具层加分支。
